# ROADMAP — 从 v1.0.0 到“日常主力”

写于 2026-11-22/23，上一个 session 的最后一份文档；2026-11-23 按用户反馈修订（去掉“先用一两周再攒摩擦”的门槛）。**这是推荐顺序，不是合同**：技术上的取舍你自己定，只把“只有他才知道的事”（日常做什么任务、口味、能接受的风险）拿来问他，一次一个问题、二选一。

## 推进规则（用户 2026-11-23 定的；与本文任何旧表述冲突时，以这一节为准）

用户的原话：“我是懒狗，不想拿着半成品硬当主力熬一两周再去攒摩擦，我只想先把 `pinew` 交给新 session 主动打磨成一个真正顺手、靠谱的主力版本再重度上手。”所以：

1. **不设“先用满 N 天/周”或“等摩擦出现”的门槛。** 没有任何一个版本的开工或发布以“他用了多久”为条件。
2. **主动、连续地推进**：按本表顺序 v1.1 → v1.2 → v1.3 → v1.4 → v1.5 → v2.0，再接 v3 以后的候选。做完一版就发布、开下一版，没人催也不停；一轮里能做完几版就做几版（每版各自提交、打 tag、更新 `STATE.md`）。**他没报摩擦 ≠ 没事做，也不是停下来的理由。**
3. **他报了摩擦就插队**：记进 `FRICTION.md`（日期 · 场景 · 现象），排到当前版本之前处理；同类第二次升为高优先级。
4. **验收用可测的标准**：`tools/check.py`、mock 场景、在真网关量一次、他在真机跑一条冒烟命令——**不用“他用了多久”**。他全力配合（跑验证命令、贴输出、二选一拍板），需要就直接要，并且把要他做的事合并成一条。
5. **只有两种情况会停下来等他**：要他拍板的事（口味、风险、不可逆的决定），或要他在 WSL 里跑一条命令才能继续的验证。结束这一轮之前，先把不依赖他答案的活做完（沙箱里的实现、mock 验证、下一版的预研）。
6. 没有“先熬两周”的缓冲，坏版本更容易到他手上，所以：`main` 随时可发布、每版都有 tag、`pinew.py update` 默认只拉 tag（`--to <tag>` 可锁定/退回）、有风险的改动先让他冒烟一次（DoD §3.4）。

## 0. 先看这几条

1. **这个模型下，钱不是瓶颈。** 一个 4.4k token 的前缀整段全价重算 = 约 $0.00066，命中 = $0.000066（[MM] 算术，FACTS A3）；中途切一次档位约 $0.0006（5k 历史）、$0.0054（4 万历史）。所以**不要为了省 $0.00001 牺牲功能**。缓存护城河要守，理由是：①长会话里 10× 的价差；②延迟；③前缀可预测、可量；④别让没用的指令/工具稀释模型的注意力。**真正的瓶颈是：用着顺不顺手、改坏了能不能撤、结果可不可信。**
2. **v1 在评测里“没测出伤害，也没测出收益”**（[DS, pi 1.3.0]，FACTS §J）。评测台已经饱和（开发题 144/144），它只能回答“有没有变差”，回答不了“有没有变好”。所以**质量靠每版的可测验收 + 真机冒烟 + 他随时报的摩擦（插队）来保证，不靠比赛，也不靠“先熬一阵再说”**；评测台只在里程碑当回归闸（见 v2.0）。
3. **一个版本 = 用户拿到手能感觉到的一件事。** 每版都能单独装、单独退回。写不出“用户会感觉到什么”的改动，先别做。
4. **别重写官方已有的。** pi 1.5.0 的 `examples/extensions/` 有 79 个示例（`plan-mode/`、`todo.ts`、`git-checkpoint.ts`、`handoff.ts`、`custom-compaction.ts`、`custom-footer.ts`、`jev-router.ts`、`notify.ts`、`tools.ts`、`subagent/`…），文档和示例就在 npm 包里（`$RT/node_modules/@earendil-works/pi-coding-agent/{docs,examples/extensions}`）。读它们的源码、改成适合我们的样子，比从零写稳；但**读过源码才用**，并量前缀。

## 1. 版本号怎么对应

- 用户说的“v1.1、v2、v3…” ≈ 这里的里程碑；中间的 1.x 是为了让每一步都能单独发出去。semver：新功能加 minor，不兼容的改动（会改 `~/.pi/agent` 里的东西、改默认行为）加 major。
- 旧文档（`archive/`）里的 “v1 / v1.1 / v1.2” 指同一套实测过的配置（安全带的补丁版本号），**等于本仓库的 `v1.0.0`**。旧路线图里写的 “v1.1 候选”（预设 `tools` 的 `+名字/-名字`）在这里归到 1.2.0。
- 每个 tag 都要有 `CHANGELOG.md` 条目（pi 在包更新时会显示它）和 `docs/STATE.md` 的更新。

### v1.1.0 机制：能装、能退、能自检　〔P0，第一件事〕

用户感觉到的：**一条命令装好/升级/退回；装完行为和以前一样。**

范围：
- `tools/pinew.py`：`status`（只读：装了什么、和基线差在哪）· `install [--dry-run]`（迁移 + 装包 + 放置配置）· `undo`。**在 `tools/legacy/install_v1.py` 的骨架上改**（先检查再动手、`--dry-run`、先写 MANIFEST、原子写入、读回核对、只撤自己装的、不碰 `models.json`/`auth.json`/`sessions/`）。
- 迁移规则（HANDOFF §5.1 的双装崩溃是死穴）：对 v1 的 12 个文件逐个比对基线哈希——一致 → 删掉复制品；被改过 → 搬进备份并提示；用户自己加的文件 → 不碰；**只按文件名精确动手，绝不整目录删**（`~/.pi/agent/` 同时是托管安装的根）。然后 `pi install <本地路径>`，再放置 `AGENTS.md`、合并 `settings.json`。
- **缺 `presets.json` 时 `--preset` 静默无效**（HANDOFF §5.2）：优先让 `preset.ts` 把包内 `config/presets.json` 当最底层默认读（单一来源，`git pull` 即生效）；做不到再让安装器放置。这是对基线文件 `preset.ts` 的**有意改动**，写进 CHANGELOG。
- **非包文件怎么同步**：pi 只从包里加载 `extensions/ skills/ prompts/ themes/`，`AGENTS.md`/`settings.json` 不是包资源，只能由安装器放置，所以光 `git pull` 同步不到它们。**默认定案（可改，但要写理由）：带哈希记录的拷贝，不用符号链接。** 理由：符号链接会让 `git pull`/切分支悄悄改掉正在使用的 AGENTS.md（运行中的会话改系统提示 = 整段缓存重付，FACTS B3）；用户改符号链接指向的文件等于弄脏仓库；`undo` 的语义也更干净。配套：`pinew.py status` 对每个放置的文件报告“同步 / 仓库有新版（可更新）/ 用户改过（只提示，绝不覆盖）/ 被删”；`pinew.py update` = `git pull`（默认拉到最新 tag，`--to <tag>` 可锁定/退回）+ 对“仓库有新版且用户没改过”的文件 `sync` + 自检，是用户以后升级要敲的**唯一**命令。`settings.json` 只合并我们拥有的键（`defaultThinkingLevel`、`showCacheMissNotices`），不整体覆盖。`presets.json` 按上一条让 `preset.ts` 读包内默认，这样非包文件只剩 `AGENTS.md` 和 `settings.json`。
- `tools/check.py`（沙箱里一条命令，无网络、不花钱、≤2 分钟）：①包加载无重复无报错（`dev/rpc_commands.py`）②安全带仍拦 `rm -rf old`（print 模式）③`--preset explore/deep` 生效（工具表 + 指令都变）④三轮会话前缀逐轮严格追加（mock 的请求转储）⑤发给模型的 system+tools 与基线快照字节一致（有意改动要 `--update-golden` 并写 CHANGELOG）⑥基线文件哈希 ⑦密钥扫描 ⑧安装器场景（假 HOME：全新 / 复制式 v1 / 被改过的 v1 / 带用户自己的文件 / 被强杀的断点），`undo` 后与安装前逐字节一致。
- `tools/smoke.*`（用户在 WSL 跑，两三条命令，<$0.002）：迁移前后各跑一次固定的 `pi -p … --mode json --no-session`，对比首个请求的 `input+cacheRead+cacheWrite`（应相等，容差 ±70 即已知异常 B12）。

验收：
- 沙箱：`python3 tools/check.py` 全绿；假 HOME 里改了仓库的 `AGENTS.md` 后 `status` 报“仓库有新版”，`update` 同步它；用户改过的那份不被覆盖。
- WSL：`pinew.py install --dry-run` 打印的计划与 `collect-state.py` 的输出一致；正式安装后 `pi list` 里 pinew 只出现一次，`dev/rpc_commands.py` 列出的命令和装之前相同；`pi --preset explore` 生效；`undo` 能回到装之前；烟测前后首请求 token 数相等。
- 前缀：`+0 tokens/request`（只是搬家，不该变）。
- 打 tag `v1.1.0`，STATE/CHANGELOG 更新。

用户要做的：贴 `collect-state` 输出 → 看 `--dry-run` 计划说“好” → 贴安装输出 → 跑烟测贴结果。（共 4 次，每次一条命令。）

### v1.2.0 开局多档位　〔P1，用户点名的第一块短板〕

用户感觉到的：**开一个会话时，一句话选到合适的“档”**，而不是在 explore 和 deep 之间凑合。

设计要点：
- **在开局选，不在中途切。** 实测中途换 thinking/工具白名单/预设指令各断一次缓存（FACTS B5），所以 `pi --preset 名字` 是主路径；`/preset` 保留，但文档里写明“一次性断缓存，约 $0.0006（5k 历史）~ $0.0054（4 万历史）”。（官方示例 `jev-router.ts` 也是“一个会话只切一次、认一次缓存未命中”。**有意的、一次性的切换可以；自动的、反复的不行。**）
- 先问用户**一个问题**：日常主要做什么（改自己的项目 / 写脚本运维 / 读别人的代码 / 混合）；再看 `pi --list-models` 和 `collect-state` 里的 models.json，才有依据决定档位要不要带 `model`（**默认不带**，没有明确的更便宜/更强的备选就不换模型）。
- 建议起点（可改）：`quick`（low，全套四工具，指令“最小改动、先做再说”）· `explore`（v1，只读）· `deep`（v1，high，全工具 + 验证）· `review`（只读 + 看 diff）· 有便宜模型时加 `cheap`（机械批量活）。每个档位一行用途说明，进 `/preset` 的列表。**不单列 `plan` 档**：“计划”现在有三个入口会撞车——v1.0 的 `/plan` 提示模板（一次性消息，不限制工具）、一个 `plan` 预设、v1.4 要采用的官方 `plan-mode/`（也叫 `/plan`，带 `pi --plan` 开局进入、工具限制、步骤追踪）。**定案：一条计划路径、替代而不是并存**——v1.2 不造 `plan` 预设（要只读探索用 `explore`，要计划暂时用 `/plan` 模板）；v1.4 采用 `plan-mode/` 后删掉 `prompts/plan.md`，启动器里的 `pp`（若做了）改成 `pi --plan`（见 v1.4）。
- 启动方式：别让用户记一串参数。可选：安装器可选地在 `~/.local/bin/` 放几个小启动脚本（如 `pq`/`pe`/`pd`/`pr`，`undo` 会删；计划入口的 `pp` 要等 v1.4 采用 `plan-mode/` 后再加，内容是 `pi --plan`）或让用户一次性粘贴几行 alias——**问他一次，二选一**。
- **修 preset 的 tools 与 MCP 的坑**（FACTS G3）：读源码所得 [src]——`preset.ts` 用 `pi.setActiveTools(validTools)` 整体替换工具表，所以 MCP 入口（`codemode`/`tool_search`/`mcp__*`）被一并关掉；而 CLI 的 `--tools` 文档说“MCP 工具默认保留，除非条目以 `mcp__` 开头”，且支持纯 `+名字/-名字` 的相对写法。办法：在 `preset.ts` 里保留当前已启用的 MCP 入口，或让预设的 `tools` 支持 `+名字/-名字`。
- **修“预设盖掉命令行 `--thinking`”**（FACTS G7，11-23 在沙箱复测）：`preset.ts` 文件头写着 “CLI flags always override preset values”，但 `--preset` 在 `session_start` 里应用，比 pi 在 `main.js` 里把 `--thinking` 当会话创建参数应用晚，所以 `pi --preset deep --thinking low` 实际发出去的是 high（`budget_tokens` 16384）、`pi --preset explore --thinking high` 发出去的是 low（2048）。`--tools` 没这个问题（它是外层白名单，预设只能在里面取交集）。做法你定：应用预设后，若命令行显式给了 `--thinking`（`--thinking X`、`--thinking=X`；`--model 名:档位` 的简写也会设档位），就改回去；做不到至少打一行提示。这是对基线文件 `preset.ts` 的**有意改动**，和 v1.1 里“读包内 presets”的改动一起写进 CHANGELOG；`check.py` 加断言（`--preset deep --thinking low` → 2048），`dev/seed-check.sh` 里现在把“预设赢”记作已知坑的那一项，到时翻成“命令行赢”。
- **编码档要不要带 `grep`/`find`/`ls`**：现在只有 `explore` 有它们，`quick`/`deep` 是默认四件套。FACTS §C 只量了默认四件套（+1,013 token/请求），这三个工具在 MiniMax 上**没量过**（旧估算 [DS, pi 1.3.0，mock 字符数÷3.6] 约 +0.61k，别当数）。做法：① 在真网关各发一个请求量首请求前缀差（`tools/real-gateway/see_body.py`，<$0.001）；② 小 A/B：同一批“在陌生代码库里找东西再改”的任务，每臂 ≥5 次 + 对照臂（FACTS B11），**判据先写**（例：轮数降 ≥15% 或成功率升才带，否则不带）。`bash` 里本来就能 `grep`/`find`，所以收益可能是 0；缓存命中时 +0.6k token 只值约 $0.00001/请求，真正的问题是它们有没有帮模型少绕路。结果写进 FACTS。
- 每个档位的首请求前缀（token）要**在用户的真网关上量一次**（`tools/measure-tiers.py`，每档一条 `pi --preset X -p … --mode json`，总共 <$0.005），结果写进 FACTS 并标 `[MM, pi 1.5.0]`。mock 的 token 数是近似的，别当真。

验收：
- `check.py` 新增：每个档位启动后，请求里的工具表和指令与设计一致；带一个 MCP 服务器（`labs/lesson6/mcp/mini_mcp.js`）时，开局 `--preset explore` 和中途 `/preset explore` 之后 MCP 入口都还在。
- 用户的真机：每档各起一次，测量表贴回；`/preset` 列表里每档一行用途说明；`FRICTION.md` 里已有的档位相关条目逐条对照处理（没有就写“无”）。**不等他“用一周”，也不要求他“不再手改配置”才算过。**
- 前缀：`quick` 档 ≤ v1 默认 + 150 token（纪律，不是铁律；超了要在 CHANGELOG 说明换来了什么）。

### v1.3.0 撤得回（+ 逐轮花费/命中）　〔P2〕

用户感觉到的：**agent 改坏了，一句 `/undo` 回到我这条消息之前；每轮结束能看到这一轮花了多少、命中多少。**

- 官方 `git-checkpoint.ts`（53 行）已读：每轮 `turn_start` 做一次 `git stash create`，只在 `/fork` 时提示还原，且 `agent_settled` 就清空 → **不够当 undo**，`git stash create` 也**不含未跟踪文件**。要做的是：检查点要跨轮保留（建议放 `refs/pinew/…` 而不是 stash 列表）、包含未跟踪文件（临时 index 技巧）、`/undo` 先给“撤销前”再做一个检查点（撤销本身可撤销）、非 git 目录优雅降级成一行提示、**绝不对用户未提交的改动做无检查点的 `reset --hard`/`clean`**。
- **检查点粒度：每条用户消息一次（`before_agent_start`），不要每个 `turn_start` 都做。** 一条用户消息里模型常常连调很多轮工具（[DS, pi 1.3.0] round 2 里 v1 臂的开发题单次运行最多 19 轮），每轮都把工作区（含未跟踪文件）全量扫一遍，在大仓库里会拖慢每一步；而 `/undo` 的语义本来就是“撤回我这条消息之后的改动”，一次够了。树与上一个检查点相同就不新建（`before_agent_start` 在 triggerTurn 时也会触发，FACTS F2，靠这个去重）。**加保护**：检查点设时限（例如 5 秒，超了放弃并显示一行“这条消息没有检查点”，绝不卡住 agent）；未跟踪文件设数量/体积上限（超了只给跟踪文件做检查点并提示，别把没被 `.gitignore` 挡住的构建产物全塞进去）；上限先让用户在他最大的仓库里量一次检查点耗时（只读、一条命令）再定。
- **逐轮花费/缓存命中，本版就做**（不必等他开口要）：pi 的 footer **已经**显示**累计** token、花费、上下文占用（docs/usage.md），缺的只是“这一轮”。一个只观察的小扩展：读 `message_end` 里的 `usage`（`custom-footer.ts` 是现成模板），每轮结束在状态栏显示“本轮 $… · 命中 …% · 输入/输出 …”，可用环境变量关。`showCacheMissNotices` 已开，别重复提示。**纯 UI，0 前缀。** 校验：各轮之和 = pi 的 `/session` 合计（mock 和真机各对一次）。若它和 `/undo` 不是同一天做完，可单独发 1.3.1。
- 纯扩展代码 0 前缀；`/undo` 是命令不是工具。

验收：在临时 git 仓库里用 mock 脚本让“模型”改几个文件 + 新建一个未跟踪文件 → `/undo` 全部还原（含未跟踪）→ 再 `/undo` 的撤销也能撤；非 git 目录不报错；一个造出来的大仓库（数万文件）上检查点在时限内完成，或按上面的规则降级并提示；逐轮花费行的各轮之和 = `/session` 合计；0 前缀。用户的真机：一次真实的“改坏再撤” + 看一眼每轮花费。

### v1.4.0 不迷路：计划、待办、验证闭环　〔P2〕

用户感觉到的：**大改动前先给计划，改完自动跑测试、失败了自己接着修。**

- **计划模式（唯一的计划入口）**：先读官方 `plan-mode/`（`index.ts`+`utils.ts`，约 16 KB）：`/plan` 或 `Ctrl+Alt+P` 开关，`pi --plan` 开局就进入；计划模式把工具表换成 `read/bash/grep/find/ls/questionnaire`（bash 走只读白名单）、每条用户消息前**追加**一条 `[PLAN MODE ACTIVE]` 消息（追加，安全）、从 `Plan:` 小节抽编号步骤、执行时用 `[DONE:n]` 追踪进度。**一条计划路径，替代而不是并存**：采用它之后**删除 `prompts/plan.md`**（`/plan` 这个名字归扩展；重名时 pi 1.5.0 谁生效没查，别依赖），v1.2 不造 `plan` 预设（见 v1.2），启动器里的 `pp`（若做了）改成 `pi --plan`；CHANGELOG 里写明退役。理由：模板不限制工具、预设不追踪步骤，扩展两样都有。**缓存**：`pi --plan` 开局进入没有额外代价（工具表在开局定）；会话中途 `/plan` 切换会换工具表（断一次，FACTS B5，可接受）；退出计划模式时它的 `context` 钩子会把旧的 `[PLAN MODE ACTIVE]` 消息从请求里滤掉——这是**非追加**改动（[src] 读过源码，**没测**），要量一次断多少再决定要不要保留这个钩子。
- **待办**：`todo.ts` 注册一个工具 → **每个请求 +42 ~ +95 token**（FACTS C7）；只在需要的档位启用（工具白名单管所有工具，F3）。
- **验证闭环**（质量上收益最大、风险也最大）：模型改完文件、要收尾时，如果项目配了验证命令（例如 `.pi/verify.json`：`{"cmd":"npm test"}`，`/init` 可帮着生成），扩展跑一遍，失败就**把输出交回去并请求续跑**（追加安全，FACTS B3），每条用户消息最多 2 轮，超了就停下并汇报。默认关，用 `/verify` 或档位开启。**钩子线索**：pi 1.5.0 的 `agent_before_settle` 正是为这件事设的——它是“最后一个可操作的边界”，处理器返回 `{ entries: [...event.entries, {type:"custom_message", customType, content, display:false}], continue: true }` 就追加一条条目并保证再发一次请求；文档示例用一个布尔旗标防重复；用户按 Esc 中止时条目照提交、续跑被抑制；`agent_settled` 只是通知、不能续跑（FACTS F1；[src] 读 pi 1.5.0 的 `docs/extensions.md` 与 CHANGELOG，**没跑过**，所以先写 mock 契约测试：续跑真的多发了一个请求、计数器按用户消息重置、Esc 时不续跑）。**风险**：死循环（计数器卡死）、跑到危险命令（走安全带）、输出太长（截断到 2,000 字符以内）。
- **AGENTS.md 加一行（本版就加，不等他“碰到过”）**：“规格与测试矛盾时按规格实现、测试不动、如实报告；不要为了变绿去改测试配置或跳过测试”（FACTS J4：[DS, pi 1.3.0] p16，n=3/臂里 1 次做对、1 次沿用旧测试、1 次改 `package.json` 的 test 脚本让 `npm test` 变绿）。**不要写成“有歧义先问/停下问”**——非交互评测里没人回答，等于认输；交互使用时模型本来就可以顺手报告矛盾。每行规则约 +41 token/请求（FACTS C2），在 CHANGELOG 声明；加之前用 `tools/real-gateway/see_body.py` 在真网关量一次。**效果在 MiniMax 上没测**：写一个 p16 式的小题（README 的新规则与旧测试冲突），每臂 ≥5 次 + 对照臂，判据先写（例：改 test 脚本/跳过测试的次数、最终回答有没有披露矛盾），结果如实写进 FACTS，别夸大。会话中途改 AGENTS.md 会整段重付（FACTS B3），所以只在发版时改。

验收：mock 场景“改坏 → 验证失败 → 追加消息 → 修好 → 通过”走通且 ≤2 轮；达到上限时停下；Esc 不续跑；`pi --plan` 开局的请求里工具表是计划模式那组、`prompts/plan.md` 已删且 `/plan` 只有一个入口；前缀逐轮追加的检查仍绿；每个新增工具/规则在 CHANGELOG 声明 `prefix: +N tokens/request`。

## 3. 每个版本的完成定义（DoD）

1. `tools/check.py` 全绿（v1.1 之前用 HANDOFF §4 第 4 条的手工清单）。

## 4. 实验纪律（轻量版）

只在需要**真网关数字**时才做实验，且：
- 做之前写三行：预期是什么；这个 n 能分辨多大的差别；对照臂是什么（FACTS L7：背景会随机整段重付，长请求约 20%，所以每格 ≥5 次、必须有对照）。
- 成本控制：每个实验默认 <$0.05；要超就先告诉用户并等他点头；告诉他要花多久、会不会改机器。
- 数字写进 FACTS 之前，用原始日志复算一遍；复算不上的不写。
